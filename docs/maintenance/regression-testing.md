# セキュリティ保守の回帰テスト

`v12-mod-maintain` のパッチ前後を比較するための基盤。実データをコピーせず、
毎回空の PostgreSQL DB に実際の migration を適用し、小さなデータを API で作成する。
アプリ本体のコード、DB 定義、認証やレート制限をテスト用に変更しない。

## 実行する検証

| 層 | 観測・検証するもの |
| --- | --- |
| 既存単体テスト | 画像、暗号、メール、キューのシリアライズ、チャート集計、型境界、既修正不具合など。Jest のソースカバレッジも保存 |
| 全登録 API | 実行中のアプリから一覧・メタデータ・入出力スキーマを IPC で取得。不正トークン、認証必須、管理者・モデレーター限定、アプリ権限、宣言された不正な入力型、POST 専用 API の GET 拒否を、該当する全エンドポイントで確認 |
| 機能シナリオ | 登録・ログイン、プロフィール、MiAuth・旧アプリ認証、権限・失効、パスワード変更、TOTP、レート制限、フォロー・承認・拒否、ミュート・ブロック、投稿・返信・引用・Renote・リアクション・お気に入り・投票・削除・ピン留め、カーソルページング |
| 公開範囲 | public / home / followers / specified × 本人 / フォロワー / 無関係なユーザー / 未認証。本文が非表示になるケース、タイムラインへの混入、ActivityPub による匿名取得も確認 |

| WebSocket | main チャンネルの接続確認と、実際の Registry 更新による Redis 経由のイベント配送 |

追加時点では **312 API 中 190 API に正常系の実行がある**。
これは 190 API の全入力・全分岐を検証したという意味ではない。
API ごとの実行ケース・正常系・拒否ケース・未検証箇所を毎回生成する `inventory.md` / `inventory.json`
が現在の範囲の正本。API の追加やスキーマ変更も比較対象になる。

従来の `packages/backend/test/_e2e`・`test/tests` と Cypress は、古いモジュール構成や
DB リセット方法を含み、そのまま復活させていない。新しいシナリオは別途実行される。

## 実行方法

Node と Yarn はリポジトリ指定の版を使い、依存を frozen lockfile でインストールし、
`yarn build` でフロントエンドもビルドしておく。テスト DB は **PostgreSQL 18** を使い、
接続時にメジャーバージョンを検証する。ローカル PostgreSQL のユーザーには
テスト用 DB の作成・削除権限が必要。既存 DB の名前を渡すオプションは設けていない。

```sh
yarn test:regression:harness
# Docker で隔離した PostgreSQL 18 と Redis を起動する
yarn test:services
# 最初の一度。CI では --with-deps も指定する
node node_modules/playwright-core/cli.js install chromium

yarn test:regression
```

既存の Chromium を使う場合は `REGRESSION_CHROMIUM=/usr/bin/chromium` を指定する。
PG の接続先は `REGRESSION_PG_HOST` / `PORT` / `USER` / `PASSWORD`、
Redis は `REGRESSION_REDIS_HOST` / `PORT` で指定できる。ホストは loopback のみ許可する。
既定値は PG `127.0.0.1:54318` / `postgres`、Redis `127.0.0.1:56318`。
`yarn test:services --down` は専用ラベルを持つこの 2 コンテナだけを削除する。
PG のデータは tmpfs 上にあり、コンテナ削除時に失われる。
通常の `.config/default.yml`・`.config/test.yml` を読んだり書き換えたりしない。

生成物は `.maintenance-regression/latest/` に出る。同じ checkout での実行は直列に行う。
Actions の `Maintenance validation` でも全検証を行い、失敗時も生成済みの結果を
`maintenance-regression-<SHA>` artifact として 14 日間保存する。

実際の 3 サーバー間の HTTPS 配送・受信は、追加の
[コンテナ連合試験](federation-testing.md)で実行する。

## 比較とパッチの進め方

1. 修正前に `yarn test:regression` を通し、再現する攻撃入力と正常入力を用意する。
2. 変更する機能が `inventory.md` で未検証なら、まず専用の正常系・拒否系・保存内容の
   シナリオを追加する。一般的な認証拒否の成功を、その機能の正常系の代わりにしない。
3. 脆弱性を修正し、攻撃入力を拒否することと、正常入力の互換性を検証する。
   不具合修正・セキュリティ修正は、その挙動を示すテストと関連づける。
4. `observations.json` とコミット済みの `scripts/regression/baseline.json` に差があれば
   CI は失敗し、`behavior-diff.json` が JSON のパス・変更前・変更後を示す。
   セキュリティ修正で意図する差も例外なく出す。
5. 意図した差だけを確認して基準を更新する。`yarn test:regression:record` は候補を
   `latest/observations.json` に作るだけで、既存の基準を上書きしない。
   ケースの期待値・セキュリティ上の理由・基準 JSON の変更を同じレビューに含める。
   不明な差をまとめて承認する許可リストは設けていない。
6. パッチ前の SHA に対し次を実行する。CI の push 時には直前 SHA で自動実行する。

   ```sh
   REGRESSION_BASE_REF=<パッチ前の40桁SHA> yarn test:regression:patch
   ```

   変更したバックエンドの実行行に未実行箇所がある、または変更した分岐に未実行の
   経路があれば失敗する。カバレッジ未取得のファイルも失敗する。
   この確認だけで応答の正しさを判断せず、必ず意味のある結果の検証も加える。

## レポートの読み方

- `observations.json` / `behavior-diff.json`: HTTP のステータス・JSON・Content-Type・
  Cache-Control、WebSocket イベント、連合の出力・キュー・保存行、DB スキーマ等。
- `inventory.md` / `.json`: 全 API のケース別の実行状況。`uncovered` を明記。
- `security-inventory.md` / `.json`: 公式アドバイザリーごとの確認状況と専用テストの対応。
  修正済みとした項目にテストの対応がなければ失敗する。一般的な認証テストで
  すべてのアドバイザリーを検証済みにすることはない。
- `coverage/index.html` / `lcov.info` / `coverage-final.json`: 実プロセスの V8 カバレッジを
  ソースマップで TypeScript に対応づける。読み込まれないソースも 0 として含める。
  全体と認証・入力検証・投稿・連合の主要ファイルには、コミット済みの最低値を適用する。
  ソースマップを有効にするのはテスト用ビルドで、通常ビルドの設定は変えていない。
- `changed-coverage.json`: パッチの変更行・分岐の未実行箇所。
- `browser.json` / `browser-trace.zip` / PNG: ブラウザの要求・エラーと操作記録。
- `application.log` / `migrations.log` / `v8/`: 起動・DB 初期化・キュー処理・生の実行記録。
- `runtime-errors.json`: アプリの未処理 Promise rejection / 例外。アプリのログ出力や
  例外処理を止めずにプロセスから観測し、メッセージと発生元も基準との比較対象にする。
- `packages/backend/coverage/`: Jest 単体テスト側のカバレッジ。実プロセス側とは別に保存。

乱数 ID は同一 ID の参照関係を保った別名に置き換え、インスタンスのランダムなポート、
生成した鍵・トークン・ファイルアクセスキー・QR コード、ISO の時刻を正規化する。
null、キーの有無、公開範囲、権限の配列、要素の順序、本文、エラーコードは残す。
時刻の正しさが要件のケースでは別途明示的に比較する。チャートは応答形状を比較し、
数値の集計は既存のチャート単体テストで確認する。

## 残る範囲と限界

全挙動の網羅や、未知の脆弱性がないことを保証するものではない。特に次は追加が必要。

| 領域 | 現時点の限界・パッチ時に加えるべき検証 |
| --- | --- |
| 連合の相互運用 | 別のコンテナ連合試験で同じ版の Misskey 3 台の discovery・配送・Announce・Update・投票・リモート添付等を検証。他実装、鍵更新、LD-signature、リレー、機能の全組み合わせは未検証 |
| 外部サービス | 外向き TCP をテストプロセスで拒否し、ブラウザも同一 origin に制限。S3、OAuth 外部プロバイダー、CAPTCHA、DNS・リダイレクトを含む SSRF、URL プレビュー、RSS、SMTP サービスとの実相互運用には専用の相手役が必要 |
| セキュリティ攻撃の再現 | 全登録 API に共通の拒否検証はあるが、48 件の公式アドバイザリーすべてに攻撃再現テストがある状態ではない。`misskey-advisories.json` の適用確認・専用回帰ケースを各パッチで追加し、テスト成功だけで修正済みに変更しない |
| 非同期・運用 | Redis による権限状態の伝播を状態で待つ。複数 worker・複数ノードの競合、再起動中のジョブ、障害復旧、並行実行、長時間の漏れ、負荷・DoS は未検証 |
| 認証 | パスワード・TOTP・MiAuth・旧アプリの主要フローは検証。WebAuthn 実機、メール認証・パスワード再発行、全 cookie・CSRF 条件の検証は別途必要 |
| UI | Chromium の主要操作。全画面・各表示モード・Firefox/WebKit・モバイル・アクセシビリティ・見た目の画素比較・全 XSS 入力は未検証。操作の安定化のため装飾アニメーションは無効化 |
| DB 互換性 | 空 DB への migration と小さい再現データでの操作を確認。巨大 DB の移行時間・ロック・実行計画・データの特殊値は保証しない。スキーマやデータ変換を変更する場合は、対象の旧スキーマと特殊値を再現する小さな移行 fixture が必要 |
| バックグラウンド機能 | 削除・import/export・一括整理等の全ジョブ、すべての設定組み合わせ、OS・ネイティブ依存の全形式は未検証 |

通常の起動経路を `NODE_ENV=production` で通し、認証・CAPTCHA・レート制限を
`NODE_ENV=test` で迂回しない。daemon 起動とクラスタ化のみ止める。
DB はランダム名の `regression_*` だけを作成・削除し、Redis は固有 prefix のキーだけを
削除する。FLUSHDB/FLUSHALL は使用しない。アプリの設定とメディア書き込み先も
専用ディレクトリに隔離する。既存設定・本番データ・外部の利用者には接続しない。

カバレッジには宣言・スキーマの評価や DI 初期化も含まれる。高い行カバレッジを
機能網羅率や安全性と同一視せず、API の正常系一覧、拒否系、実際の保存結果を併せて読む。

## テストによって確認した既存不具合

アンテナの作成・更新・削除は HTTP では成功するが、`AntennaService` が Redis に渡す
`onRedisMessage` の `this` が束縛されておらず、`push` / `findIndex` / `filter` を
undefined に対して呼ぶ未処理 Promise rejection が発生する。
この 3 件は現状の基準に **既知の不具合として含める**。テストが通ることを、その機能が
正常である証明としない。修正時にはイベントによるキャッシュ反映の専用テストを追加し、
この例外が消えることも確認する。新しい例外や件数の増減は比較で失敗する。

## 追加時の実測（2026-10-23、日本時間）

- バックエンドの厳格な型検査、通常のバックエンド・クライアント・SW ビルドが成功。
- 既存 Jest 14 スイート・82 テストが成功。単体テスト側は行 46.95%、関数 26.73%。
- 隔離・比較・変更行判定・lockfile のテスト 10 件が成功。
- 実アプリの回帰テストは 1,604 観測。独立した新規 DB で再実行し、基準との差は 0。
- PostgreSQL 18 でも 1,604 観測と既存 82 テストが成功。旧 PG 15 の基準との差は、
  PG 18 がカタログに表示する 757 件の NOT NULL 制約の追加だけだった。
  制約の削除や API 応答・保存内容の変化がないことを確認して基準を更新した。
- 実アプリ側は行約 78.4%、分岐約 65.9%、関数約 71.3%。これらは別々の計測であり、
  Jest 側の割合を足したり、全機能の検証率と読んだりしない。
